# MakerVault v1.1.0 release candidate checklist

Candidate branch: `release/prepare-v1.1.0`. Until release publication, the current stable release remains **v1.0.5**.

## Verification on isolated Debian test server

1. Pull candidate branch and rebuild using `compose.yaml` and `compose.build.yaml`. Do **not** reset production data.
2. Confirm `python manage.py check`, `python manage.py migrate --check`, and `python manage.py v1_release_preflight` succeed.
3. Run the full Django suite using `python manage.py test core.tests --keepdb -v 1`; verify no failure.
4. Run frontend checks with the existing Node environment or Docker build.
5. Confirm `python manage.py shell -c "from makervault.version import VERSION; print(VERSION)"` returns `1.1.0`.
6. Record initial `python manage.py catalogue_coverage` and maintenance settings.
7. Observe an unattended due maintenance tick on the **combined** candidate, verify task dispatch, continuation across batches and saved image batch diagnostics. Normal lack of source images is not in itself a failure.
8. Test upgrade and backup/restore on a disposable copy of persistent storage, including account sign-in, images, files and roles.

## Publication steps (only after sign-off)

1. Merge this release-preparation PR and ensure all checks pass on `main`.
2. Update the MakerVault README and MakerVault-docs README, landing page, getting-started guide and any explicit stable-version references from v1.0.5 to v1.1.0 in a separate publication documentation PR.
3. Tag **the tested release commit** as `v1.1.0`. Do not move an existing release tag. The publish workflow rejects mismatched application versions.
4. Verify GitHub Actions published the intended `1.1.0` and `latest` images, then pull the correct digest/tag on a test installation before production.
5. Record release notes and confirm backup and rollback instructions.

No tag or Docker container publication is part of this PR.
